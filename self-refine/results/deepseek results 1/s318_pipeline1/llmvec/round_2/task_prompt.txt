        Tester feedback:
        The function returns `max + index + 1` using local variables that are out of scope after the loop, but more critically the logic has bugs causing wrong results:

- **`max` and `index` are uninitialized after the loop exits** if `iterations/2 == 0`, and even when the loop runs, the final `return max + index + 1` uses the local `max` and `index` variables which were last set inside the loop body — but `index` is `int` and `max` is `float`, so `max + index + 1` is fine syntactically. The real bug is the **wrong return value**: the reference likely returns `chksum` (which is `max + (float)index`), not `max + index + 1`.

- **The unrolled loop does not advance `k` correctly**: `k` starts at `inc` (after `k += inc` before the loop), but the unrolled body reads `a[k]`, `a[k+inc]`, `a[k+2*inc]`, `a[k+3*inc]` — this is correct for the first iteration, but `k` must start at `1*inc` not `0*inc`. After `k += inc` before the loop, `k = inc`, so `a[k] = a[inc] = a[1*inc]` ✓. This part is okay.

- **`end4` calculation is wrong**: `1 + ((LEN_1D - 1) & ~3)` can equal `LEN_1D` when `LEN_1D` is a multiple of 4, causing the unrolled loop to read `a[k+3*inc]` out of bounds (accessing index `LEN_1D * inc`).

- **Fix `end4`**: use `end4 = LEN_1D - ((LEN_1D - 1) % 4)` or simply `end4 = 1 + ((LEN_1D - 1) / 4) * 4` but cap it so the 4-wide read stays in bounds: `end4 = LEN_1D - 3;` (stop when fewer than 4 elements remain).
